# 电商商家管理软件 AI 技术支持：构建计划

## 一、先看最终要交付什么

**一个可以调查、恢复并验证电商软件故障的支持系统。** 商家使用终端提问，系统先根据说明回答，必要时交给第二个角色调查。需要改变状态时必须批准，操作之后查实际业务结果。无法处理时交给工程师，工程师处理后可以复查。

重点做深两条流程：

1. 平台有有效订单，但管理软件未收到。
2. 仓库已经出库，但平台发货状态未更新。

库存完成一种明确规则下的只读调查，不做库存修复。平台只影响一个渠道、商家设置错误、授权失效和未知异常是两条主线中的故障类型，不分别开发六套系统。

原始要求与实施选择的对应关系见技术方案 1.9 节。数据库合并、两条恢复主线和库存只读是本计划在授权范围内作出的选择；不是用户原话。原文“订单未送仓”补齐真实送仓与调查，额外的送仓配置恢复不列为第三条自动恢复主线。

技术选择：Python、LangChain、LangGraph、PostgreSQL + pgvector、百炼模型、小型 FastAPI 测试服务和终端操作。采用一套数据库实例；不增加 Milvus。具体原因、依赖和限制见技术方案第 4 节。

### 最终架构边界

本项目采用**顺序式多智能体工作流（Sequential Multi-Agent Workflow）**，但两个角色职责必须明确，不重复调查：

```text
商家
  ↓
Customer Agent
  ├─ 对话理解与必要澄清
  └─ Customer RAG：检索、改写、混合检索、重排、引用验证
  ↓ 自助方案无效 / 明确需要后台调查
Structured Handoff
  ↓
Support Agent
  ├─ 读取 handoff，不重复第一层已经完成的问答
  ├─ 根据当前证据动态选择内部只读工具
  ├─ Evidence 收集与验证
  └─ Diagnosis / Action Proposal
       ├─ 可解决 → 给出结果
       ├─ 需要写操作 → Approval → Execute → Verify
       └─ 仍无法解决 → Engineer Ticket
```

- **Customer Agent 是低成本自助层。** 可以为了找到正确资料而追问版本、错误码、订单号等必要信息，但不查询真实订单状态、账户权限、后台运行记录或平台状态，不做 Operational Investigation（后台调查）。
- **Support Agent 是调查层。** 接收 handoff 后可以看到第一层的客户描述、已给建议、引用和客户反馈，再额外使用内部只读工具；用户后续消息继续进入当前 Support Agent，不重新启动 Customer Agent。
- **Ticket 不是两个 Agent 之间的传输方式。** 两个 Agent 通过结构化 handoff 交换信息；Ticket 只在 Support Agent 仍无法解决、达到调查上限或用户明确要求人工时创建，作为工程师接手结果。
- **Support Agent 默认使用 Dynamic Tool Routing（动态工具路由）。** 每一步根据现有证据决定下一项最有价值的查询，证据足够时立即停止，不固定把所有工具调用一遍。
- **本期不加入 Internal RAG。** Support Agent 的核心输入是 handoff + 内部工具 + Evidence。只有真实开发案例反复证明“工具返回事实但必须依赖内部 Runbook 才能解释”时，才把 Internal RAG 作为后续扩展；不能为了技术栈完整而硬加第二套 RAG。
- **业务模拟器只服务两条主线和库存只读。** 不继续扩展退款、退货、多仓、复杂促销或更多平台差异，避免后端模拟器抢占 AI Application Engineering 的主要时间。

## 三、实施前统一的规则

1. **延续同一个程序。** 每项任务使用前面已有的入口、数据和工具，不另做一个完成后丢弃的小演示。
2. **每项当时就能运行。** 命令、处理、存储和输出接通后才算完成。该任务不需要的组件不提前加入。
3. **模型必须真的调用。** 缺模型账户就明确记为未完成；固定输出只可用于程序行为测试。
4. **故障必须由行为产生。** 例如关闭开关导致任务受阻、平台保存后延迟返回导致超时，不把“正确答案”作为工具结果。
5. **小测试随功能加入。** 比较与汇总放在专门的评测任务中，不集中补写全部测试。
6. **安全边界随入口加入。** 身份与公司过滤从第一项做；批准与重复安全从首次写入做，任务 10 是扩展恢复情况。
7. **任务未到不假装已具备。** 例如任务 06 遇到未知问题先保存“待人工处理”；任务 13 才接上完整工单。最终交付必须把这些阶段连接起来。
8. **说明与代码同时变化。** 操作规则变了，更新文档版本、案例预期与引用，不能让第一层按旧规则指导。
9. **保留真实失败。** 每个任务在提交前检查改动并运行相关测试；记录实际通过项、失败项和未验证项。是否提交代码另由用户决定，本计划本身不授权提交。
10. **第一层不做后台调查。** Customer Agent 只负责对话澄清和 Customer RAG；若需要读取真实业务状态、账户权限、后台记录或平台状态，直接 handoff 给 Support Agent。
11. **第二层动态调查，不机械遍历工具。** Support Agent 根据当前 Evidence 决定下一项工具；设置可配置的最大调查步数/工具预算，证据足够、工具无替代证据或达到上限时停止并给出结果或升级。默认预算由开发集测量后确定，不在计划里拍脑袋固定。
12. **持续记录可观测数据（Observability）。** 每次模型、检索、重排、工具和写操作记录 trace/run ID、名称、输入范围、成功/失败、耗时、token/用量和可得成本；不保存或展示模型隐藏思维过程。Task 14 只汇总这些已有记录，不临时补造。
13. **不提前增加第二套知识系统。** Customer RAG 是本期唯一文档检索层；Support Agent 先使用 handoff、内部工具和 Evidence。只有真实案例证明 Internal RAG 能解决重复出现的知识缺口时再单独立项。

## 四、逐项任务

### Task 01 — 在终端回答一个真实产品问题

**依赖：无。**

**新增能力：** 商家能输入中文问题，收到基于实际检索资料的回答，并看到来源及会话编号。

**真实数据流：** 终端问题 → 身份映射 → 问题向量 → PostgreSQL 中的资料片段 → 真实模型 → 回答与引用 → 保存会话、消息和调用用量 → 终端显示。

**文件与工作：**

- 创建 `pyproject.toml`、`.env.example`、`.gitignore` 和 `compose.yaml`，先只运行 PostgreSQL 与 pgvector。读环境文件使用 `python-dotenv` 并在依赖中声明，避免依赖终端隐藏配置。安装后生成 `requirements.lock`；记录实际版本到 `docs/versions.md`。
- 编写 `app/cli.py`、`app/config.py`、`app/db.py`、`app/auth.py`、`app/models.py`、`app/docs.py`、`app/customer.py`、`app/graph.py`、`app/trace.py`。不要一次建全部工具。
- 聊天入口从本任务支持 `--conversation`：读取权限范围内的已有会话并继续第一层问答，供任务 02 的追问复用；任务 05 再增加交接后的当前角色路由。
- 创建 `db/001_support.sql` 和 `lab/bootstrap.py`，建立预置身份、资料、会话、运行记录和框架检查点。测试令牌由本机生成，不写入文档或提示词。
- `docs/product/` 先写 12 篇短说明，至少包含订单同步开关、订单接收资格、商品编号、发货事实与平台状态区别。明确这是本测试产品的规则。
- `docs/sources.md` 记录行业参考；`prompts/customer.md` 限制只能依据可见的本产品资料给操作建议。
- 建立 `evals/dev.jsonl` 的 6 个问答和 `evals/price_config.json`；`tests/test_docs.py`、`tests/test_access.py` 随功能加入。`README.md` 写下当前可运行步骤。

**如何验证：**

按技术方案 8.6 节启动数据库与初始化。运行 `python -m app.cli doctor`，确认实际模型和向量调用成功且向量长度为 1024。然后运行资料导入，提问“如何开启订单同步？”

应看到答案、资料标题、片段编号、会话编号；数据库中存在这次输入、回答和运行记录。再问“这个系统能自动退款吗？”应说明本期不提供，不编造操作路径。

**测试与完成条件：** 导入两次不重复新增相同片段；无效令牌拒绝；B 公司用户不能读取 A 公司资料。至少 6 个问答真实运行并保留结果。缺模型调用量时标记未知，不写零费用。

**边界或阻塞：** 需要模型账户与可用地域。任务 01 必须验证所选模型支持工具调用和结构输出；此时只有第一层，不宣称已完成两个角色。

### Task 02 — 用不同问法找到正确说明

**依赖：Task 01，复用资料与聊天入口。**

**新增能力：** 商家用口语、错误码或不完整信息提问时，系统能选择资料范围、追问或补查一次。

**真实数据流：** 用户问题 → 选择使用说明/规则/排查资料 → 按身份和版本过滤 → 语义查找与中文关键词查找 → 合并候选 → 原有模型回答 → 保存两路结果和回答。

**文件与工作：**

- 扩展 `app/docs.py`，增加 jieba 分词与 `rank_bm25`，保留完整商品编号、错误码和常见中英文混合词。
- 两路各取前 15，按倒数名次合并并去重，最多 20。提供 `vector_only` 与 `hybrid` 两种配置。
- 扩展 `app/customer.py` 和 `prompts/customer.md`：不明产品版本先问；缺少能影响资料检索的关键信息先问；最多改写一次再查。澄清只服务于检索和理解，不允许第一层查询真实订单状态、账户权限、后台记录或平台状态。
- `docs/product/` 增加本产品渠道 A/B 差别和旧版本说明。扩展 `evals/dev.jsonl`，包括“单子进不来”和完整错误码的不同问法。
- 在 `app/trace.py` 保存过滤条件和两路排名，在 `tests/test_docs.py` 验证过滤先于排序。

**如何验证：** 分别提问“店铺的单子一直不进来怎么办？”与“ORDER_SYNC_DISABLED 是什么意思？”；比较两种模式实际命中的片段。再提出缺少店铺信息的具体异常，系统应追问而不是假定渠道。

**测试与完成条件：** 同一问题不会把其他公司的资料拼入候选；旧版本操作不能覆盖当前版本；一次追问后能接着回答；最多两轮检索。报告开发问答中哪类因关键词查找受益，不预设必须全部更好。

**边界或阻塞：** 本期几百片段，关键词索引在过滤后的内存集合建立即可。不增加搜索服务器，不做大规模性能宣传。

### Task 03 — 检查答案是否真的有依据

**依赖：Task 02，复用两路检索结果。**

**新增能力：** 商家获得经过候选重排和引用检查的回答，无依据的关键结论被删除或标为不确定。

**真实数据流：** 两路候选 → 实际调用重排服务 → 前五片段 → 模型生成结论与引用 → 编号/权限/版本检查 → 无工具的语义检查 → 修正后的答案与记录。

**文件与工作：**

- 在 `app/docs.py` 接入 `qwen3-rerank`，增加 `hybrid_rerank` 配置和真实用量记录。
- 增加 `app/citations.py`、`prompts/citation_check.md`，程序先检查引用存在性，模型再检查资料是否支持结论。检查调用计入统一调用上限。
- 扩展 `app/customer.py` 输出结构，保存 `claims`、引用片段与被删除结论的简短原因。
- 添加无答案、相近错误、过期资料和恶意文档案例；扩展 `tests/test_docs.py`。

**如何验证：** 询问“开启同步就能把所有历史订单都导入吗？”资料只允许指定订单补处理时，回答不能扩大为全部历史订单。插入一条带“忽略权限”的测试资料，不能改变程序权限。

**测试与完成条件：** 伪造片段编号被拒绝；有效链接但内容无关不能算支持；重排不可用时记录降级并使用已经实现的混合候选，关键结论仍需检查。三种检索配置都真实运行至少一轮，人工复核关键结论。

**边界或阻塞：** 语义检查有误判可能，不声称它保证答案正确。重排服务访问不通时该集成尚未完成，不能只交付降级路径。

### Task 05 — 交接并动态调查订单为什么缺失

**依赖：Task 03、Task 04，复用问答和真实订单记录。**

**新增能力：** 商家提问后，第一层可以交接；第二层能查询实际证据、继续追问并指出受阻步骤。

**真实数据流：** 商家问题 → Customer RAG 给出自助说明 → 仍未解决时第一层只补齐 handoff 所需标识 → 保存结构化 handoff 与当前角色 → Support Agent 读取 handoff → 根据当前证据动态选择下一项内部只读工具 → 保存 Evidence → 证据足够时停止 → 返回事实、可能原因和下一步。

**文件与工作：**

- 创建 `app/support.py`、`app/tools.py`、`app/evidence.py`、`prompts/support.md`，扩展 `app/graph.py`。`SupportHandoff` 至少保留客户描述、第一层 RAG 回答与引用、客户已尝试步骤/反馈、已知业务标识和未解决原因，避免第二层重复问答。
- 实现 `handoff_to_support`、`get_shop_status`、`get_order`、`get_process_records`、`check_connection`。这些后台工具只绑定 Support Agent；Customer Agent 不拥有调用权限。
- Support Agent 每次工具返回后重新判断“证据是否已足够 / 下一项最有价值的工具是什么 / 是否需要客户补充必要标识 / 是否应该停止并升级”，不写死为固定工具序列。
- 扩展 `app/cli.py` 的继续会话和 `case show`；身份从会话及账户重新核对。交接后同一会话的下一条用户消息继续进入 Support Agent，不重新跑 Customer Agent。

- 创建 `tests/test_tickets.py`，增加伪造批准、恶意日志、跨商家会话等已有入口的整体验证。

**如何验证：** 运行未知异常或库存更新失败案例，产生一个工单；工程师用 `ticket show` 查看。再次提交同一会话不会创建第二个未关闭工单。未分配工程师或其他商家无法读取。

**测试与完成条件：** 证据链接可定位真实记录；没有证据的原因不能写成确定结论；直接人工请求有效；模型或资料不能借建单扩大权限；所有等待人工路径都能生成可接手材料。

**边界或阻塞：** 工单保存在本项目，不连接外部工单系统，不实际发送邮件或企业消息。工程师修改真实业务的动作不由模型自动决定。

### Task 14 — 比较方案并生成可核查的效果报告

**依赖：Task 13，复用完整会话和逐步累积的案例。**

**新增能力：** 项目使用者能运行指定案例集，比较不同检索和调查方式，得到实际结果、成本和失败清单。

**真实数据流：** 案例文件 → 隔离测试数据与实际故障 → 商家真实模型会话 → 案例指定的批准角色按批准路径操作 → 实际业务结果 → 独立检查 → 汇总报告。

**文件与工作：**

- 完成 `evals/run.py`、`lab/checks.py` 和 `app/report.py`，命令加入 `app/cli.py`。最终案例数：开发 50、保留 30，构成见技术方案 8.2 节。
- 评测程序设置业务和批准脚本，模型只能看到商家描述与实际工具结果；批准仍调用同一身份检查，不直接写 `approved`。
- 比较三种检索方式；固定顺序与动态工具调查；单角色与两角色。所有对照保留相同身份、写入限制、资料和结果检查。动态调查除成功率外还比较平均工具调用数、无效工具调用数和调查耗时，避免只证明“能跑”。
- 完整系统对 30 个保留案例各执行三次。对照使用开发集中固定的 20 个案例：8 问答、6 订单、6 发货。检索比较运行 8 × 3 × 2 次，调查比较运行 12 × 2 × 2 次，角色比较运行 20 × 2 × 2 次，共 176 次；具体分组与技术方案 8.3 节一致，不混淆独立案例数与运行次数。
- `tests/test_eval.py` 检查指标分母、失败计数、重复次数和无价格配置时的处理。
- 保留运行编号、版本、原始用量、遮盖后的记录，以及按案例逐条判断的结果；从现有 trace 汇总每案模型调用次数、retrieval/rerank latency、工具调用次数、总 latency、token/用量和可得成本。

**如何验证：** `python -m app.cli eval run --suite evals/dev.jsonl --mode full --repeat 1`；再运行预设对照与保留集。用 `eval compare` 生成摘要，并抽查至少五个报告结论是否与原始事实一致。

**测试与完成条件：** 报告包括成功、失败、正常无需修复和应人工案例；不把用户未确认的问答算修复；假成功、越权、未批准写入、重复业务单列；所有模型调用及失败重试计入耗时和用量。安全回归出现任何问题不得完成最终验收。

**边界或阻塞：** 案例和测试必须在前面的任务中持续建立，Task 14 只负责统一运行、比较和汇总，不从零补造全部案例。真实模型费用取决于账户地域与模型，运行前按价格配置估算并设置用户选择的预算上限。达不到目标如实报告，不换分母。

### Task 15 — 在新环境交付可复查的完整支持流程

**依赖：Task 14，复用全部已通过能力。**

**新增能力：** 另一名开发者能启动系统复现问题；工程师处理外部原因后可发起复查，工单依据实际结果关闭或保持打开，并导出完整过程。

**真实数据流：** 干净启动 → 测试环境产生问题 → 商家问答/调查/升级 → 工程师在测试环境完成允许的人工处理 → `ticket recheck` 运行同一验证器 → 更新工单 → 导出可读报告。

**文件与工作：**

- 扩展 `app/tickets.py`、`app/verify.py`、`app/report.py` 和 `app/cli.py`，加入复查及遮盖后 HTML 导出。有订单、发货或库存目标时按对应事实复查；使用咨询、缺业务编号的工单返回 `NEEDS_INFO` 并保持打开，本期不冒充已验证修复。
- 复用任务 04 的 `Dockerfile` 并完成 `compose.yaml`；使用独立 `init` 服务先初始化，再启业务服务。为 `support`、`lab`、`init` 分别提供最小环境，不把故障控制和保留答案打进共用镜像或挂载给支持程序。
- 完成 `README.md`、`docs/versions.md`、`docs/demo.md`。列清实际命令、配置名、已验证限制和数据来源。
- 三条演示脚本：带引用和检索对照的自助问答；Support Agent 动态工具调查后批准恢复；未知异常带 Evidence 交工程师并复查。响应丢失作为恢复可靠性测试保留在报告，不让演示重点被后端故障模拟淹没。
- `tests/test_tickets.py` 加复查关闭和复查失败重开；在新目录或新容器卷中用独立运行编号验收，不删除其他项目数据。
- 整理实际评测报告和短录屏；指标缺失就保留待补，不编造提升百分比。

**如何验证：** 按技术方案 8.6 节运行完整容器启动、资料导入和场景命令。新用户只靠 README 就能走完三条演示。工程师处理演示时，由测试操作者先用 `connection restore` 或关闭已知测试故障恢复外部条件，再通过正常业务任务重试或商家新批准的恢复步骤使目标状态更新。工程师最后运行 `ticket recheck`；仅恢复授权但订单仍缺失时必须保持工单打开，只有业务结果满足条件才关闭。

**测试与完成条件：** 两条主线全部成功与必要失败路径重新通过；库存只读边界不变；安全回归全部通过；报告能追溯到具体运行；分享产物没有密钥或其他商家内容。最终必须列出未接真实平台、受控场景范围、小样本评测等限制。

**边界或阻塞：** 本机可复现交付属于本期范围；公共云部署和真实客户试用不在本期。不能因为页面能打开就宣布项目完成。

## 六、遇到困难时怎么做取舍

| 发生的情况 | 应采取的动作 | 不能采取的替代 |
| --- | --- | --- |
| 模型账户不可用 | 明确阻塞真实模型能力，继续完成可独立进行的业务服务工作 | 用固定文本冒充模型集成 |
| 重排效果没有提升 | 保留实验能力，默认使用表现更好的配置并说明 | 修改案例使新方案看起来更好 |
| 工具经常超时 | 检查服务、超时设置和记录，减少无效调用 | 无限重试或把超时当空数据 |
| 自动恢复容易出错 | 缩小允许动作，保留批准、验证和升级 | 自动改数据库绕过规则 |
| 保留集出现失败 | 报告失败；修正后将其作为已见案例，新增独立保留案例再验证 | 调到通过后仍称从未见过的测试 |
